1. Introducción

1.1 Descripción del proyecto

Este proyecto es una tienda online de productos ecológicos llamada Campo Fresco. Está desarrollada íntegramente con tecnologías web del lado del cliente: HTML5, CSS3 y JavaScript puro (sin frameworks). Para la persistencia de datos se utiliza la API localStorage del navegador, lo que permite simular una base de datos sin necesidad de servidor.

El proyecto se ha desarrollado de forma progresiva a lo largo de 6 semanas, empezando desde una estructura HTML muy básica y añadiendo funcionalidades cada semana hasta llegar a la versión final completa. Esta metodología de trabajo por fases nos ha permitido ir aprendiendo y aplicando los conocimientos de forma ordenada.

1.2 Objetivos

  • Crear una aplicación web funcional y estética para una tienda de productos ecológicos.
  • Implementar un sistema de autenticación (login y registro) con validaciones completas en los formularios.
  • Desarrollar un CRUD completo para la gestión del catálogo de productos desde un panel de administración.
  • Practicar el almacenamiento en el cliente con localStorage simulando una base de datos.
  • Aplicar buenas prácticas de diseño: sidebar de navegación, mensajes de feedback, confirmación antes de borrar.
  • Diseñar e implementar un sistema de copias de seguridad automatizado para el entorno de desarrollo (parte de Sistemes).
  • Trabajar de forma organizada con un tablero Kanban y un repositorio GitHub.

2.2 Estructura de la aplicación

La versión final (Fase 6) está compuesta por cuatro páginas interconectadas:

  • index.html — Página de inicio con hero, sección de características y productos destacados cargados dinámicamente.
  • productos.html — Tienda completa con todos los productos, filtros por categoría y buscador en tiempo real.
  • login.html — Página de autenticación con dos pestañas (iniciar sesión / crear cuenta) y validaciones completas.
  • admin.html — Panel de administración con CRUD de productos, solo accesible si hay sesión activa.

2.3 Flujo de la aplicación

  1. El usuario llega a index.html y puede explorar los productos destacados sin estar registrado.
  2. Si quiere comprar, puede añadir productos a la cesta (se guarda en localStorage).
  3. Para gestionar productos, necesita ir a login.html y registrarse o iniciar sesión.
  4. Una vez autenticado, el sidebar muestra el enlace al panel de Administración.
  5. Desde admin.html puede añadir, editar o eliminar productos del catálogo.
  6. Cualquier cambio se refleja automáticamente en index.html y productos.html.

3. Desarrollo por Fases

El proyecto se desarrolló durante 6 semanas, mejorando la aplicación de forma progresiva. Cada fase añade funcionalidades sobre la anterior.

Fase 1 Estructura base (Semana 1 — ~5h)

Primera versión con HTML y CSS básico. Página de inicio con hero, 4 productos hardcodeados, modal de registro con CSS puro (checkbox hack), carrito con alert(). Sin JavaScript complejo.

Fase 2 Carrito con localStorage (Semana 2 — ~6h)

Se añade una segunda página (productos.html) con 10 productos en categorías. El carrito pasa a usar localStorage con un panel lateral deslizante. CSS reorganizado con variables CSS (:root). Animaciones de hover.

Fase 3 Login y registro real (Semana 3 — ~7h)

Se crea login.html con dos pestañas. Los usuarios se guardan en localStorage. Validaciones: email con formato correcto, contraseña mínimo 6 caracteres, contraseñas deben coincidir, email no duplicado. Mensajes de error debajo de cada campo.

Fase 4 Panel admin y CRUD (Semana 4 — ~8h)

Se desarrolla admin.html. Los productos ya no están hardcodeados en el HTML: se almacenan en localStorage como array de objetos y se cargan dinámicamente. CRUD completo: añadir, editar (formulario pre-rellenado) y eliminar (con confirm() nativo). Formulario con validaciones.

Fase 5 Sidebar y filtros (Semana 5 — ~7h)

Rediseño completo del layout: el menú horizontal se convierte en un sidebar vertical fijo a la izquierda usando display: flex en el body. Se añaden filtros de categoría (botones) y buscador en tiempo real (evento input). Validaciones visuales con sombra y borde de color.

Fase 6 Versión final con backend real (Semana 6 — ~10h)

La gran novedad de esta fase es la integración con un servidor Linux real. Se crea una API REST en PHP que conecta con MariaDB, y la web pasa de usar localStorage a peticiones fetch reales al servidor:

  • API REST en PHP: archivos login.php, registro.php, sesion.php, logout.php y productos.php en la carpeta /api/.
  • Base de datos MariaDB: tablas usuarios (id, nombre, email, password hasheado) y productos (id, nombre, precio, categoria, descripcion, imagen).
  • Servidor Nginx: el proyecto se despliega en un servidor Ubuntu (IP: 192.168.0.20, puerto 8082) con Nginx + PHP-FPM.
  • Modal de confirmación personalizado para el borrado de productos (sin confirm() nativo).
  • Sistema de notificaciones toast que reemplazan todos los alert() del proyecto.

Las fases 1-5 usaban localStorage para todo. En la Fase 6, los datos de usuarios y productos se guardan en la base de datos del servidor, lo que permite que varios usuarios accedan y los cambios persistan entre sesiones y dispositivos.

4. Sistema de Copias de Seguridad (Parte Sistemes)

4.1 Fase 1 — Análisis del proyecto

4.1.1 Elementos a proteger

Nuestro proyecto Campo Fresco está alojado localmente en XAMPP. Los elementos que necesitamos proteger son:

ElementoUbicacion en servidorCriticidadPor que?
Codigo fuente/var/www/campofreso/AltaSi se pierde, perdemos semanas de trabajo
Base de datos MariaDBcampofrescodb (usuarios + productos)AltaDatos reales de usuarios y catalogo de productos
Config Nginx/etc/nginx/sites-enabled/campofreso.confMediaSin ella el servidor no sabe como servir la web

4.1.2 Riesgos especificos de nuestra web

Despues de analizar nuestro proyecto concreto, identificamos los siguientes riesgos:

  • Borrado accidental del codigo: Si alguien elimina la carpeta /var/www/campofreso/ del servidor, perdemos todo el trabajo. Es el riesgo mas probable.
  • Fallo del disco del servidor: Si el disco del servidor Linux falla, se pierde tanto el codigo como la base de datos.
  • Corrupcion de la base de datos: Un fallo durante una escritura en MariaDB podria dejar tablas corruptas. Los datos de usuarios y productos se perderian.
  • Perdida de registros: Al tener usuarios y productos reales en la base de datos, un fallo sin backup supone perder informacion de clientes.
Justificacion de la frecuencia: El proyecto esta en desarrollo activo y la BD cambia cada vez que se añaden usuarios o productos. Hacemos copias de lunes a viernes a las 23:00h con cron. En el peor caso, perdemos el trabajo de un dia.

4.3 Fase 3 — Implementación técnica

4.3.1 Script backup.sh — Puntos clave

Creamos el archivo /home/valle/backup/backup.sh. Los 4 pasos que realiza son:

# 1. Comprimir proyecto en tar.gz con fecha y hora tar -czf "${TAR}" -C /var/www campofreso # 2. Exportar base de datos con mysqldump mysqldump -u"${DB_USUARIO}" -p"${DB_PASS}" "${DB_NOMBRE}" > "${SQL}" # 3. Generar hash SHA256 para verificar integridad despues sha256sum "${TAR}" > "${HASH}" # 4. Eliminar backups de mas de 7 dias automaticamente find "${DESTINO}" -name "backup_*.tar.gz" -mtime +7 -delete

4.3.2 Automatizacion con cron (Linux)

Para ejecutar el backup automaticamente cada dia, configuramos una tarea cron con el comando crontab -e:

# Ejecutar backup.sh de lunes a viernes a las 23:00h 0 23 * * 1-5 /home/valle/backup/backup.sh

La sintaxis de cron es: minuto hora dia-mes mes dia-semana. El 1-5 indica de lunes (1) a viernes (5). Esto lo añadimos con: crontab -e y añadiendo la linea anterior.

4.4 Fase 4 — Mejora y seguridad

4.4.1 Eliminación automática de copias antiguas

El script usa el comando forfiles para eliminar automáticamente los ZIP, SQL y SHA256 con más de 7 días. Así la carpeta de backup no crece indefinidamente y no ocupa demasiado espacio en disco.

4.4.2 Verificacion de integridad con hash SHA256

Cada vez que se crea un backup, el script genera un archivo .sha256 con el hash del tar.gz usando sha256sum de Linux. Para verificar que un backup no se ha corrompido, creamos el script verificar.sh:

# Verificar integridad de todos los backups disponibles sha256sum --check "${HASH_FILE}" # Resultado si el backup esta bien: backup_2026-04-29_06-37.tar.gz: OK # Resultado si el backup esta corrupto: backup_2026-04-29_06-37.tar.gz: FAILED

El script restaurar.sh verifica automaticamente la integridad antes de restaurar, y avisa al usuario si el hash no coincide antes de continuar.

4.5 Fase 5 — Restauración (OBLIGATORIA)

Para demostrar que el sistema funciona de verdad, realizamos dos pruebas de restauración completas.

4.5.1 Prueba de restauracion del proyecto

  1. Ejecutamos backup.sh manualmente y confirmamos que se crea el tar.gz en /home/valle/backup/backups/.
  2. Borramos la carpeta /var/www/campofreso/ del servidor: sudo rm -rf /var/www/campofreso.
  3. Comprobamos que al abrir http://192.168.0.20:8082/Fase6/ aparece un error 404.
  4. Ejecutamos restaurar.sh, seleccionamos el backup creado y confirmamos.
  5. Abrimos http://192.168.0.20:8082/Fase6/ y verificamos que la web vuelve a funcionar.
Resultado: La web volvio a funcionar correctamente tras la restauracion. Todos los archivos HTML, CSS, PHP e imagenes se restauraron sin problemas.

4.5.2 Prueba de restauracion de la base de datos

  1. Conectamos a MariaDB y eliminamos la BD: mysql -e "DROP DATABASE campofrescodb;".
  2. Recreamos la BD vacia: mysql -e "CREATE DATABASE campofrescodb;".
  3. Restauramos desde el archivo SQL del backup: mysql campofrescodb < backup_FECHA.sql.
  4. Verificamos en MariaDB que las tablas y datos vuelven a existir correctamente.
Resultado: La base de datos (10 productos + 1 usuario) se restauro correctamente desde el archivo SQL del backup.

5. Conclusiones

Este proyecto ha sido una experiencia muy completa porque hemos tenido que combinar el desarrollo web con la administracion de sistemas, que son dos cosas muy diferentes pero que en el mundo real siempre van juntas.

En la parte de desarrollo web, la progresion de las 6 fases nos ha permitido ver claramente como mejora una aplicacion: empezamos con HTML estatico y acabamos con una API REST en PHP conectada a MariaDB. Lo mas interesante fue implementar el sistema de login con sesiones PHP reales y ver como el frontend (JavaScript) se comunica con el backend (PHP) mediante fetch y JSON. Tambien aprendimos a hacer validaciones de formularios propias, con feedback visual en tiempo real.

El cambio mas visible entre la primera fase y la ultima fue la arquitectura completa: de archivos estaticos en local a una aplicacion web cliente-servidor desplegada en Linux. Anadir el sidebar lateral, el modal de confirmacion y los toast notifications hace que la aplicacion parezca mucho mas profesional.

En la parte de sistemas, aprendimos a configurar un servidor Linux real con Nginx, PHP-FPM y MariaDB desde cero. Los scripts de backup en shell (bash) son mas potentes que los .bat de Windows, y usar cron para automatizar las copias es lo que hacen los administradores de sistemas en el mundo real. Ahora cuando hagamos cualquier proyecto lo primero que configuraremos sera un backup automatico con verificacion de integridad.

Si tuvieramos mas tiempo, anyadiriamos una pasarela de pago simulada para completar el flujo de compra, y mejorariamos el sistema de backup para que envie un email de confirmacion automatico cuando se ejecute correctamente (o una alerta si falla).
